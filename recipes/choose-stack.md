# Как выбрать AI-стек для 1С

## Статус проверки

Логика выбора прошла документальный review 8 августа 2026 года. Это архитектурная инструкция: конкретный инструмент нужно дополнительно проверить по его записи в [catalog/tools.json](../catalog/tools.json). End-to-end стенд 1С для этого маршрута ещё не опубликован.

Не начинайте с названия модели или MCP-сервера. Сначала определите поверхность доступа и действие, которое система теоретически способна выполнить.

## 1. Что должен делать AI

| Задача | Нужные данные | Минимальная поверхность | Что запрещено по умолчанию |
|---|---|---|---|
| Писать или проверять BSL | Исходники и справка | Копия XML/EDT-выгрузки | Доступ к рабочей базе |
| Понимать структуру конфигурации | Метаданные, иногда исходники | Offline dump или read-only metadata endpoint | Выполнение произвольного кода |
| Запускать сборку и тесты | Локальная среда разработки | Allowlist конкретных CLI/EDT operations | Удаление проекта/базы, update production DB |
| Строить отчёты | Ограниченный набор данных | Отдельная роль 1С + минимальный OData/API | Запись, проведение и удаление |
| Создавать документы | Справочники и документы | Отдельный write gateway | Действие без preview и подтверждения |
| Работать с Bitrix24 | REST API конкретного портала | Docs MCP + runtime с минимальными scopes | Универсальный webhook с лишними правами |

## 2. Где находятся данные

- **Копия XML/EDT** — лучший старт для разработки и code review.
- **Одноразовая тестовая база** — обязательна для первой интеграционной проверки и негативных тестов записи.
- **Рабочая база** — только после server-side запретов, журналирования и проверки восстановления.
- **Облачная 1С** — опубликованный OData может поддерживать запись; возможности провайдера нужно проверить отдельно.
- **Закрытый контур** — локальная модель снижает внешнюю передачу данных, но не ограничивает права MCP tools.

## 3. Какой уровень риска допустим

| Уровень | Разрешения | Пример | Минимальная проверка |
|---|---|---|---|
| Низкий | Только копия исходников | AI объясняет модуль | Diff и статический анализ |
| Средний | Чтение тестовой базы | AI строит сверочный отчёт | Эталон + контрольные суммы |
| Повышенный | Чтение production | AI анализирует дебиторку | Запрет записи на стороне 1С + audit log |
| Высокий | Запись production | AI готовит документ | Dry-run, preview, approval, лимиты, rollback |

Если сценарий решается на более низком уровне, не повышайте доступ.

## 4. Проверка инструмента до установки

1. Откройте запись проекта в [catalog/tools.json](../catalog/tools.json).
2. Проверьте `source_revision`, `verification.level` и `maintenance.status`.
3. Просмотрите `access.mutating_operations` и `destructive_operations`.
4. Сверьте ОС, версию 1С/EDT и prerequisites.
5. Установите зафиксированный release/commit в изолированную среду.
6. Сначала включите только read-only preset или allowlist tools.
7. Зафиксируйте expected output и все отклонения.

Особые случаи:

- `EDT-MCP`: поддерживаются EDT 2026.1/2026.2; начинайте с `Analysis Only` или `Code Review`, не с `All Tools`.
- `code-index-mcp`: для BSL нужен `bsl-indexer`; стандартный npm `code-index` предназначен для других языков.
- `mcp-1c-v1`: это RAG структуры конфигурации на Python/Docker/Qdrant, не анализатор BSL.
- `1c-trusted-gateway`: экспериментальный Windows-only проект с arbitrary code execution; название не заменяет security review.

## 5. Минимальный pilot

1. Выберите одну измеримую задачу.
2. Подготовьте 10–30 тестовых примеров без персональных данных.
3. Зафиксируйте правильные ответы или текущий результат процесса.
4. Запустите сценарий на копии исходников или одноразовой базе.
5. Проверьте позитивный результат и отказ запрещённых действий.
6. Измерьте точность, время, стоимость и число ручных исправлений.
7. Сохраните версию, config без секретов, логи и rollback.
8. Только после review расширяйте поверхность доступа.

## 6. Критерии выбора

- явная лицензия;
- понятный data flow и модель auth;
- server-side разделение чтения и записи;
- документация установки с версиями;
- фиксируемый release или commit;
- журналирование без секретов;
- возможность ограничить tools и объекты;
- воспроизводимый smoke-test;
- понятный rollback;
- активность сопровождения.

Не выбирайте проект только по числу звёзд или по словам `secure`, `trusted` и `production` в названии.
