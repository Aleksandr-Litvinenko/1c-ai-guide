# Read-only бизнес-аудит 1С

## Статус проверки

Архитектура и checklist прошли документальный review. Отдельно опубликованы [подтверждённый автором private live-smoke подключения к 1С:Фреш и пример тестового POST](1cfresh-odata.md), но полный end-to-end с серверным запретом записи и восстановлением одноразовой базы ещё не пройден. До такого теста маршрут нельзя считать готовой инструкцией для production.

Цель: находить управленческие отклонения без изменения данных.

> **OData 1С не является read-only.** Стандартный интерфейс может создавать, изменять, удалять объекты и проводить документы. Запрет должен действовать на стороне 1С/API; список MCP tools и prompt — только дополнительный слой.

## Подходящие первые контроли

- дебиторы с просроченной оплатой;
- отрицательные остатки;
- резкий рост закупочной цены;
- продажи ниже себестоимости;
- дубли контрагентов;
- документы без ответственного или договора;
- аномальное изменение выручки по неделям;
- расхождения между задачами Bitrix24 и учётом времени.

## Безопасная схема

```text
одноразовая обезличенная база
  → отдельный пользователь 1С без прав записи
  → минимальный состав OData/API
  → GET-only gateway при необходимости
  → allowlist аналитических tools
  → AI-клиент
```

## Порядок pilot

1. Создайте отдельную тестовую копию и проверьте восстановление backup.
2. Обезличьте персональные и коммерчески чувствительные данные.
3. Выберите один контроль, короткий период и 10–30 пограничных примеров.
4. Сохраните эталонный отчёт 1С, число строк и контрольные суммы.
5. Создайте отдельную роль/пользователя без прав добавления, изменения, удаления и проведения.
6. Опубликуйте только необходимые сущности OData/API.
7. Проведите позитивный тест чтения и негативные тесты мутаций.
8. Повторно сравните число строк, суммы и маркеры целостности.
9. Сохраните config без секретов, версии, логи и результат теста.
10. Только после review проектируйте production read access.

## Негативная матрица записи

Выполняйте её **только в одноразовой тестовой базе** на специально созданном fixture-объекте.

| Проверка | Ожидаемый результат | Дополнительная сверка |
|---|---|---|
| `GET` fixture | `200` и ожидаемые поля | Число строк и checksum совпадают |
| `POST` тестового marker | `401`, `403` или server-side policy denial | Новая запись не появилась |
| `PATCH` fixture | Отказ до изменения | Поля fixture не изменились |
| `DELETE` fixture | Отказ до удаления | Fixture существует |
| Проведение документа | Операция недоступна | Статус и движения не изменились |

`400` из-за неправильного payload не доказывает отсутствие прав записи. Нужен именно server-side отказ или независимая проверка неизменности данных. После теста восстановите snapshot и повторно сверьте контрольные суммы.

Первоисточник возможностей OData: [1C:Enterprise Developer Guide](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Developer_Guides/1C_Enterprise_8.3.23_Developer_Guide/Chapter_17._Integration_with_external_systems/17.4._Standard_OData_interface/17.4.1._General_information/?language=en).

## Правила результата

AI должен возвращать проверяемую основу:

- период и организацию;
- версию конфигурации и источника;
- использованные сущности и фильтры;
- число обработанных записей;
- контрольные суммы;
- критерий отклонения;
- ссылки или идентификаторы объектов;
- ограничения и степень уверенности.

## Чего не делать

- Не использовать административную учётную запись.
- Не считать OData или MCP read-only по названию.
- Не открывать весь состав OData «на всякий случай».
- Не отправлять персональные данные во внешнюю модель без правового основания.
- Не принимать текстовый вывод AI без сверки сумм и пограничных случаев.
- Не проводить негативные write-tests на production.
- Не включать запись в рамках read-only pilot.
