# Подключение к OData в 1С:Фреш

**Русский** · [English](1cfresh-odata.en.md) · [← К гайду](../README.md)

## Статус проверки

По подтверждению автора, 8 августа 2026 года приватная интеграция `task2bitrix24` прошла HTTPS-аутентификацию и ограниченное чтение справочника из 1С:УНФ в 1С:Фреш. В локальном рабочем коде также реализованы поиск дублей, создание непроведённых документов `Document_УчетВремени` и `Document_ЗаданиеНаРаботу`, а проведение вынесено в отдельный вызов.

Это **author-reported private live-smoke для чтения**, а не независимо воспроизводимый публичный тест. Запись повторно не запускалась при подготовке гайда: пример `POST` нужно воспроизвести на одноразовой тестовой копии, прежде чем повышать статус до end-to-end.

Исходный кейс: [документация OData в task2bitrix24](https://github.com/Aleksandr-Litvinenko/task2bitrix24/blob/main/docs/ODATA.md).

## Что подключалось на практике

Claude или Codex не подключались к базе «магически». Агент помог написать и запустить обычный локальный HTTP-клиент:

```text
Codex / Claude
  → локальный клиент с ограниченными командами
  → HTTPS + HTTP Basic Auth
  → standard.odata в 1С:Фреш
  → тестовая или рабочая 1С:УНФ
```

Это важная граница: пароль знает локальный процесс, но его не нужно вставлять в prompt, MCP config, README или чат.

## Подготовка в 1С:Фреш

1. В менеджере сервиса откройте приложение и выберите **Настройка автоматического REST-сервиса**.
2. На вкладке **Авторизация** создайте отдельного служебного пользователя 1С с минимальными правами.
3. На вкладке **Состав** разрешите только необходимые объекты конфигурации.
4. Для чтения не выдавайте права добавления, изменения, удаления и проведения.
5. Для теста записи используйте отдельную одноразовую копию с синтетическими данными и проверенным snapshot.

Форма адреса в исходном кейсе:

```text
https://1cfresh.com/a/sbm/<base-id>/odata/standard.odata
```

Официальная инструкция: [1С:Фреш — работа через стандартный OData](https://1cfresh.com/articles/data_odata).

## Секреты только в локальном окружении

Сначала введите по очереди адрес, имя служебного пользователя и пароль через stdin, чтобы реальные значения не остались в shell history:

```bash
read -r ONEC_ODATA_BASE_URL
read -r ONEC_ODATA_USER
read -rs ONEC_ODATA_PASSWORD
export ONEC_ODATA_BASE_URL ONEC_ODATA_USER ONEC_ODATA_PASSWORD
```

Адрес при вводе имеет форму `https://1cfresh.com/a/sbm/<base-id>/odata/standard.odata`. Для постоянного сервиса используйте secret manager, а не shell profile или `.env` в репозитории.

Не запускайте `env`, `set`, `curl -v` или отладочную печать заголовков рядом с этими значениями. Если пароль попал в чат или лог, смените его.

Скрипт [`fresh_odata_example.py`](../scripts/fresh_odata_example.py) использует только стандартную библиотеку Python, проверяет TLS-сертификат и никогда не печатает `Authorization`.

Скрипт принимает только HTTPS endpoint домена `1cfresh.com` и отклоняет HTTP redirects: Basic Auth не должен автоматически перейти на другой origin.

## Шаг 1. Прочитать `$metadata`

Сначала узнайте реальные имена сущностей конкретной конфигурации:

```bash
python3 scripts/fresh_odata_example.py entity-sets --contains 'Document_'
```

Не угадывайте имя по пользовательскому заголовку. Ресурс строится из типа и имени объекта в конфигурации: например, `Document_УчетВремени` или `Catalog_Сотрудники`.

## Шаг 2. Прочитать список документов

```bash
python3 scripts/fresh_odata_example.py list 'Document_УчетВремени' \
  --select 'Ref_Key,Number,Date,Posted,Комментарий' \
  --orderby 'Date desc' \
  --top 10
```

По умолчанию бизнес-значения скрыты, но `Ref_Key` остаётся видимым для следующего шага. Флаг `--show-sensitive` показывает выбранные значения; используйте его только в доверенном локальном терминале, понимая, что вывод команды, запущенной агентом, попадёт в контекст Codex или Claude.

Что происходит:

- запрос отправляется через `GET`;
- `$select` ограничивает поля;
- `$top` ограничивает объём ответа;
- кириллическое имя сущности кодируется в URL;
- скрипт понимает ответы вида `value` и старый формат `d.results`.

Для следующей порции используйте `--skip 10`, затем `--skip 20`. На большой базе сначала задайте узкий `$filter` по периоду и только потом увеличивайте объём.

## Шаг 3. Прочитать один документ

Возьмите `Ref_Key` из предыдущего ответа и подставьте его вместо тестового UUID:

```bash
python3 scripts/fresh_odata_example.py get \
  'Document_УчетВремени' \
  '11111111-1111-1111-1111-111111111111' \
  --select 'Ref_Key,Number,Date,Posted,Комментарий'
```

Фактический ресурс имеет вид:

```text
Document_УчетВремени(guid'<Ref_Key>')
```

Не сохраняйте полный production-ответ в issue или публичный лог: комментарии, сотрудники и суммы могут содержать персональные и коммерческие данные.

## Шаг 4. Подготовить fixture документа

Состав обязательных полей зависит от конфигурации и её версии. Для `Document_УчетВремени` в исходной УНФ использовалась такая структура:

```json
{
  "Date": "2026-08-08T12:00:00",
  "DeletionMark": false,
  "Posted": false,
  "Организация_Key": "<guid-from-disposable-test-base>",
  "СтруктурнаяЕдиница_Key": "<guid-from-disposable-test-base>",
  "Сотрудник_Key": "<guid-from-disposable-test-base>",
  "Автор_Key": "<guid-from-disposable-test-base>",
  "ХозяйственнаяОперация_Key": "<guid-from-disposable-test-base>",
  "ДатаС": "2026-08-03T00:00:00",
  "ДатаПо": "2026-08-09T00:00:00",
  "Комментарий": "Будет заменён уникальным тестовым marker",
  "Операции": [
    {
      "LineNumber": "1",
      "ВидРабот_Key": "<guid-from-disposable-test-base>",
      "Номенклатура_Key": "<guid-from-disposable-test-base>",
      "Всего": 1,
      "ПнДлительность": 1,
      "Сумма": 0
    }
  ]
}
```

Это схема реального кейса, а не универсальный готовый payload. Сначала изучите `$metadata` и один синтетический документ-образец в своей тестовой базе. Не переносите `Ref_Key`, `Number`, `DataVersion` и GUID из production.

## Шаг 5. Создать непроведённый тестовый документ

`Posted: false` означает реальную запись, а не dry-run. Сначала получите отпечаток **уже проверенного одноразового endpoint**:

```bash
python3 scripts/fresh_odata_example.py write-fingerprint
```

Команда не открывает сеть и печатает строку вида `DISPOSABLE_TEST_BASE_ONLY:<fingerprint>`. Сверьте адрес базы вручную, затем введите эту строку в `ONEC_ODATA_ALLOW_WRITE`. Отпечаток привязывает подтверждение к точному URL, но не способен сам доказать, что база тестовая.

```bash
read -r ONEC_ODATA_ALLOW_WRITE
export ONEC_ODATA_ALLOW_WRITE

python3 scripts/fresh_odata_example.py create \
  'Document_УчетВремени' \
  './fixture.json' \
  --request-id 'work-time-guide-001' \
  --confirm-test-write
```

Скрипт:

1. сверяет подтверждение с отпечатком текущего endpoint;
2. разрешает запись только в `Document_*` и отклоняет fixture со служебными полями или `Posted: true`;
3. строит стабильный marker из `--request-id` и ищет его до записи;
4. выполняет один `POST`, получает `Ref_Key` и повторно читает объект;
5. при неопределённом результате `POST` сначала повторяет поиск marker, а не запись;
6. проверяет, что документ существует, marker совпал, а `Posted` остался `false`.

Скрипт намеренно **не** вызывает `.../Post()` и **не** удаляет документ. После проверки восстановите snapshot одноразовой базы и подтвердите, что fixture исчез.

## Защита от дублей

Публичный скрипт использует стабильный `--request-id` в строковом поле `Комментарий`; для другого реквизита задайте `--marker-field` только после проверки его строкового типа в `$metadata` и добавьте его в fixture. Служебные поля, `Posted`, `DeletionMark`, `Date` и ссылочные ключи запрещены. Повтор той же команды сначала найдёт существующий marker. Не меняйте request ID после timeout, иначе защита от повтора потеряет смысл.

В исходной интеграции дополнительно выполнялся точный поиск документа по сотруднику и периоду. Для своего документа выберите естественный ключ, выполните `$filter` и создавайте объект только при пустом результате.

Проверка до записи снижает риск, но не устраняет гонку двух параллельных запросов. Для критичной интеграции нужна серверная уникальность, очередь или блокировка на стороне приложения.

## Что нельзя делать на рабочей базе

- Не проверяйте права пробным `POST`, `PATCH` или `DELETE` на production.
- Не вызывайте `.../Post()` без отдельного preview и подтверждения человеком.
- Не отключайте TLS через `verify=False`, `curl -k` или аналоги.
- Не используйте администратора 1С.
- Не открывайте все сущности OData «на всякий случай».
- Не считайте OData read-only: интерфейс умеет создавать, менять, удалять и проводить объекты.

## Типовые ошибки

| Ошибка | Что проверить |
|---|---|
| `401` | логин, пароль и право пользователя на OData |
| `403` | права на конкретный объект и операцию |
| `404` | адрес базы, публикацию OData и точное имя EntitySet |
| `400` | обязательные реквизиты и их типы в `$metadata`; это не доказательство запрета записи |
| timeout | размер выборки, узкий `$select`, период в `$filter`, сетевой доступ |

## Промпт для Codex или Claude

Значения уже должны быть введены в локальное окружение, а не в текст запроса:

```text
В локальном окружении настроены ONEC_ODATA_BASE_URL, ONEC_ODATA_USER
и ONEC_ODATA_PASSWORD. Не показывай их значения, не печатай окружение,
Authorization или полный URL базы.

Работай только в режиме чтения:
1. Получи $metadata и найди точные EntitySet.
2. Выполни list с узким $select, $filter и $top не больше 10.
3. Не добавляй --show-sensitive без моего отдельного разрешения.
4. Для выбранного Ref_Key выполни get.
5. Не вызывай create, POST, PATCH, DELETE, Post() или Unpost().
6. Не сохраняй сырой ответ в репозиторий, issue или лог.
```
