# Связка 1С-Коннект + Jira + Bitrix24

**Русский** · [English](connect-jira-bitrix24.en.md) · [← К гайду](../README.md)

## Статус проверки

| Часть связки | Что реально сделано | Чего это не доказывает |
|---|---|---|
| Jira Data Center | **live-smoke 13 августа 2026**: анонимные запросы к публичному `https://issues.apache.org/jira` — поиск по JQL, `startAt`/`maxResults`/`total`, чтение задачи по ключу, форма ошибки HTTP `400`. Воспроизводится без учётной записи | Поведение закрытого корпоративного инстанса, права, кастомные поля |
| Jira Cloud | **docs**: endpoint, модель пагинации и обязательный `fields` взяты из документации Atlassian | Здесь не выполнялся ни один вызов к Cloud |
| 1С-Коннект | **docs**: имена операций, параметры, структура ответа `ValueTable` и часовые лимиты взяты из официальной публичной документации API. SOAP-конверт собран по опубликованному образцу | Ни одного live-вызова: у автора гайда нет доступа к порталу 1С-Коннект |
| Bitrix24 | Переиспользован проверенный read-only путь из [инструкции по задачам](bitrix24-tasks.md) | Ничего нового относительно той инструкции |
| Логика сверки и бюджет вызовов | 21 unit-тест без сети и без секретов | Что ваши три системы связаны именно так |

Это **не** end-to-end проверка связки. Живьём подтверждена только Jira-часть. Прежде чем доверять отчёту, повторите шаги 3 и 4 на своём стенде.

## Зачем это нужно

У франчайзи и внутренней ИТ-службы одна и та же работа живёт в трёх системах:

```text
клиент пишет в 1С-Коннект   → заявка на обслуживание
консультант ведёт работу     → задача Bitrix24
разработчик правит код       → задача Jira
```

Ни одна из трёх систем не знает о двух других. В результате появляются четыре типовые дыры:

- заявка закрыта, а баг в Jira ещё открыт — клиенту сказали «готово» раньше времени;
- задача Jira закрыта, а заявка висит — клиента забыли уведомить;
- заявка есть, а задачи нет нигде — работа не учтена и не оплачена;
- задача есть, а заявки нет — работа делается без запроса клиента.

Скрипт [`connect_jira_bridge_example.py`](../scripts/connect_jira_bridge_example.py) читает три системы и печатает только расхождения. Он ничего не создаёт и не меняет.

## Три системы — три разных мира

Это главное, что нужно понять до написания кода. AI-агент, который «просто сходит в API», сломается на каждой строке этой таблицы.

| | 1С-Коннект | Jira Data Center | Jira Cloud | Bitrix24 |
|---|---|---|---|---|
| Протокол | SOAP 1.2 (веб-сервисы «1С:Предприятие 8.3») | REST | REST | REST |
| Получение списка | `ServiceRequestRead` с `PeriodFrom` | `GET /rest/api/2/search` | `POST /rest/api/3/search/jql` | `tasks.task.list` |
| Пагинация | нет: возвращаются объекты, изменённые с момента | `startAt` + `total` | `nextPageToken`, `total` **не возвращается** | `next` → `start` |
| Исходящие вебхуки | **нет** | есть | есть | есть |
| Ограничение | 120 вызовов/час днём, 600 ночью | — | — | лимиты по методам |
| Авторизация | Basic, права администратора портала | Bearer PAT | Basic `email:token` | секрет в URL вебхука |

### Следствие 1. У 1С-Коннект нет вебхуков — только опрос

1С-Коннект не умеет постучаться к вам сам. Единственный способ узнать о новой заявке — периодически вызывать `ServiceRequestRead`, передавая момент последнего успешного чтения. Документация прямо говорит, что API отдаёт список объектов, изменённых с указанного момента, и требует от внешней стороны самой хранить метку актуальности.

Это меняет архитектуру: нужен не обработчик события, а планировщик с состоянием.

### Следствие 2. Часовой лимит — главный ограничитель

`ServiceRequestRead` — 120 вызовов в час днём. Это один опрос в 30 секунд, и всё. `ServiceRequestHistory` — всего 50 в час, зато принимает пакет до 550 ID за раз.

Отсюда правило: **историю нельзя запрашивать по одной заявке в цикле**. Агент, который решит «пройдусь по каждому тикету и посмотрю историю», сожжёт часовой лимит на 50 заявках и заблокирует весь сервис до конца окна.

Скрипт держит локальный бюджет и останавливается сам:

```bash
python3 scripts/connect_jira_bridge_example.py budget
```

```text
ServiceRequestHistory: осталось 50 из 50 вызовов в час
ServiceRequestRead: осталось 120 из 120 вызовов в час
```

Локальный бюджет не заменяет серверный лимит — он лишь не даёт агентскому циклу выжечь окно раньше, чем это заметит человек.

### Следствие 3. Jira Cloud и Data Center — это два разных API

Старые endpoint'ы `/rest/api/2/search` и `/rest/api/3/search` в Jira **Cloud** отключены: их гасили постепенно с августа по октябрь 2025 года. Замена — `POST /rest/api/3/search/jql`, где пагинация идёт по `nextPageToken`, поле `total` больше не возвращается, а список `fields` нужно передавать явно.

В Jira **Data Center** ничего этого не произошло: `GET /rest/api/2/search` со `startAt` и `total` работает — это проверено живым запросом при подготовке инструкции.

Практический вывод для российских команд: Atlassian ушёл с рынка, поэтому у большинства стоит именно Data Center, а вся свежая документация и почти все ответы моделей описывают Cloud. AI-агент уверенно напишет код под Cloud, получит `404` или `410` и начнёт «чинить» авторизацию вместо endpoint'а.

Скрипт определяет вариант по хосту и сам выбирает endpoint:

```python
def jira_flavor(base_url: str) -> str:
    host = urlparse(base_url).netloc.lower()
    return "cloud" if host.endswith(".atlassian.net") else "datacenter"
```

Это эвристика, а не гарантия: Cloud на своём домене или прокси перед Data Center её обманут. Если сомневаетесь, задайте вариант явно и проверьте один запрос вручную.

## Внешний ключ: поля Field1…Field5

Естественного общего ключа у трёх систем нет. Но у заявки 1С-Коннект есть пять настраиваемых строковых полей `Field1`…`Field5` по 1000 символов — они и предназначены для таких связей.

Договоритесь один раз и зафиксируйте в регламенте: например, `Field1` хранит строку вида

```text
JIRA:PROJ-123 B24-456
```

Скрипт вытаскивает оба ключа регулярными выражениями:

```bash
python3 scripts/connect_jira_bridge_example.py reconcile \
  --days 7 \
  --jql 'project = PROJ AND updated >= -7d' \
  --key-field Field1
```

Заявки без ключа попадают в отдельную корзину «без внешнего ключа» — это честнее, чем угадывать связь по времени и клиенту. Сопоставление по косвенным признакам даёт ложные пары, а на них потом строятся выводы о деньгах и сроках.

## Подготовка доступов

### 1С-Коннект

1. В кабинете администратора откройте **Администрирование → Настройки API** и включите доступ к API серверов. Там же задаётся часовой пояс, в котором сервис отдаёт время, и видна статистика вызовов.
2. Учтите: операции API выполняются пользователем с правами администратора 1С-Коннект. Отдельной read-only роли для API публичная документация не описывает — это существенное ограничение, и его нужно компенсировать на своей стороне.
3. Адрес веб-сервиса для России, Казахстана, Беларуси, Туркмении, Таджикистана, Узбекистана, Киргизии и Вьетнама — `https://cus.1c-connect.com/cus/ws`, для ЕС — `https://eu-cus.1c-connect.com/cus/ws`. Сервис называется `PartnerWebAPI2`.

Раз ключ администраторский, доступ к нему должен быть уже, чем к самому порталу: отдельный секрет, отдельный процесс, журнал вызовов, и никакого агента, которому этот секрет виден напрямую.

### Jira

Data Center — персональный токен, Cloud — пара `email` и API-токен:

```bash
read -r JIRA_BASE_URL
read -r JIRA_EMAIL          # только для Cloud, для Data Center оставьте пустым
read -rs JIRA_TOKEN
export JIRA_BASE_URL JIRA_EMAIL JIRA_TOKEN
```

Токену достаточно права на просмотр нужных проектов. Не выдавайте право на переходы статусов: скрипт всё равно не умеет их вызывать, а лишнее право переживёт этот скрипт.

### Bitrix24

Переиспользуется вебхук из [инструкции по задачам](bitrix24-tasks.md) — с правом только на задачи:

```bash
read -r BITRIX24_EXPECTED_HOST
read -rs BITRIX_WEBHOOK
export BITRIX24_EXPECTED_HOST BITRIX_WEBHOOK
```

## Шаг 1. Проверить Jira, ничего не подключая

Эту команду можно выполнить прямо сейчас, без учётной записи и без своего инстанса — она ходит в публичный Jira фонда Apache:

```bash
export JIRA_BASE_URL='https://issues.apache.org/jira'
python3 scripts/connect_jira_bridge_example.py jira-issues \
  --jql 'project=KAFKA AND created>=-3d ORDER BY created DESC' \
  --top 3
```

Фактический вывод при подготовке инструкции:

```text
Jira (datacenter): найдено 3
  KAFKA-20934 | Open (new) | <скрыто:109>
  KAFKA-20933 | Patch Available (indeterminate) | <скрыто:51>
  KAFKA-20932 | Patch Available (indeterminate) | <скрыто:76>
```

Темы скрыты по умолчанию. Флаг `--show-sensitive` их раскроет — помните, что вывод команды, запущенной агентом, попадёт в контекст модели.

В скобках указана **категория** статуса, а не его название: `new`, `indeterminate`, `done`. Названия статусов в каждом проекте свои, и сравнивать по ним нельзя; категория — единственное, что переносимо между проектами. Именно на ней построена сверка.

## Шаг 2. Прочитать заявки 1С-Коннект

```bash
python3 scripts/connect_jira_bridge_example.py connect-tickets --days 7 --top 10
```

Команда собирает SOAP-конверт по опубликованному образцу:

```xml
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope"
               xmlns:par="http://buhphone.com/PartnerWebAPI2"
               xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <soap:Header/>
  <soap:Body>
    <par:ServiceRequestRead>
      <par:Params>
        <Property xmlns="http://v8.1c.ru/8.1/data/core" name="PeriodFrom">
          <Value xsi:type="xs:dateTime">2026-08-06T00:00:00</Value>
        </Property>
      </par:Params>
    </par:ServiceRequestRead>
  </soap:Body>
</soap:Envelope>
```

Пространство имён `buhphone.com` — историческое: так сервис назывался раньше. Это не опечатка и менять его нельзя.

Ответ приходит таблицей значений: сначала идут описания колонок, затем строки, где значения расположены **позиционно**.

```xml
<Property name="ResultData" xmlns="http://v8.1c.ru/8.1/data/core">
  <Value xsi:type="ValueTable">
    <column><Name>ServiceRequestID</Name>…</column>
    <column><Name>Number</Name>…</column>
    <row>
      <Value xsi:type="xs:string">721b4536-df5c-11e9-…</Value>
      <Value xsi:type="xs:string">AAKUT-0000083</Value>
    </row>
  </Value>
</Property>
```

Поэтому разбирать ответ нужно, сопоставляя строку со списком колонок по порядку, а не по именам внутри строки — имён там просто нет. Не привязывайтесь к порядку полей из документации: берите порядок из блока `column` конкретного ответа.

Полезные поля заявки: `Number`, `CreateTime`, `ClientID`, `ExecutorID`, `ServiceRequestStatusID`, `Priority` (`LOW`, `STANDARD`, `HIGH`), `ResultValidation` (`NO_VALIDATION`, `NOT_REQUIRED`, `CONFIRMED`, `REJECTED`), `Description`, `Result`, `Duration` в секундах и `Field1`…`Field5`.

## Шаг 3. Сверить три системы

```bash
python3 scripts/connect_jira_bridge_example.py reconcile \
  --days 7 \
  --jql 'project = PROJ AND updated >= -7d' \
  --key-field Field1
```

Отчёт состоит из пяти корзин: заявки без внешнего ключа, заявки без задачи Jira, заявки без задачи Bitrix24, «задача Jira закрыта, а заявка ещё открыта» и «заявка закрыта, а задача Jira в работе». Совпавшие строки не печатаются: смысл отчёта — короткий список того, что требует решения человека.

## Что скрипт намеренно не делает

- Не вызывает ни одной операции записи: список разрешённых операций 1С-Коннект — `ServiceRequestRead` и `ServiceRequestHistory`, Bitrix24 — только `tasks.task.list`, и попытка собрать конверт для любой другой операции завершается ошибкой.
- Не создаёт задачи по заявке и не меняет статусы. Автосоздание кажется очевидным следующим шагом, но именно оно превращает ошибку сопоставления в мусор сразу в трёх системах.
- Не следует за редиректами: учётные данные не должны уехать на другой origin.
- Не печатает темы, описания и маркеры без `--show-sensitive`.
- Не хранит секреты: всё берётся из переменных окружения.

## Промпт для Codex или Claude

```text
В локальном окружении настроены CONNECT_WS_BASE_URL, CONNECT_WS_USER,
CONNECT_WS_PASSWORD, JIRA_BASE_URL, JIRA_TOKEN, BITRIX24_EXPECTED_HOST
и BITRIX_WEBHOOK. Не показывай их значения и не печатай окружение.

1. Сначала выполни budget и покажи остаток часового лимита.
2. Если остаток ServiceRequestRead меньше 5, остановись и скажи мне.
3. Выполни reconcile за 7 дней с моим JQL.
4. Не добавляй --show-sensitive без отдельного разрешения.
5. Не предлагай создавать задачи и не вызывай методы записи ни в одной
   из трёх систем.
6. Если Jira ответит 404 или 410, сначала проверь вариант инстанса
   (Cloud или Data Center), а не токен.
```

## Типовые ошибки

| Симптом | Что проверить |
|---|---|
| Jira `404` или `410` на поиске | Cloud или Data Center: у Cloud старый `/search` отключён, нужен `POST /rest/api/3/search/jql` |
| Jira `400` с `errorMessages` | JQL ссылается на несуществующий проект или поле; текст ошибки приходит в теле |
| 1С-Коннект `ResultCode` не `SUCCESS` | Текст ошибки лежит в `ResultData`; проверьте включённый доступ к API и права администратора |
| Пустая таблица заявок | `PeriodFrom` позже, чем последние изменения; учтите часовой пояс из настроек API |
| Локальный бюджет исчерпан | Дождитесь окна. Повторы не ускорят: серверный лимит считает те же вызовы |
| Строки заявок «съехали» по полям | Разбор привязан к порядку полей из документации вместо блока `column` конкретного ответа |
