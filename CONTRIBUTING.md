# Как внести вклад

Спасибо, что помогаете сделать AI-инструменты для 1С понятнее и проверяемее.

## Что можно предложить

- новый open-source инструмент;
- исправление факта, ссылки, лицензии или уровня риска;
- воспроизводимый рецепт;
- проверку совместимости с конкретной ОС или AI-клиентом;
- улучшение security baseline;
- перевод.

## Требования к проектам

Для добавления проекта укажите:

1. Ссылку на публичный репозиторий и проверенный commit SHA.
2. Одно проверяемое предложение о назначении.
3. Способ подключения к 1С, Bitrix24 или среде разработки.
4. Доступ к исходному коду, метаданным, бизнес-данным и внешним сервисам.
5. Операции записи и удаления, включая произвольное выполнение кода.
6. Режим по умолчанию и способ технически ограничить права.
7. Лицензию или отметку, что она не объявлена.
8. Требования к ОС, runtime, платформе 1С и внешним компонентам.
9. Инструкцию запуска и ссылку на воспроизводимое доказательство проверки.

Мы не принимаем:

- закрытые продукты без технической документации;
- платное размещение;
- накрученные метрики и просьбы об обмене звёздами;
- рекламные описания без проверяемых фактов;
- примеры с реальными паролями, токенами или персональными данными.

## Изменение каталога

1. Добавьте или измените запись в `catalog/tools.json` по схеме v2.
2. Используйте уникальный `id` в нижнем регистре через дефис.
3. Зафиксируйте полный `source_revision`, ветку `source_ref` и дату `reviewed_on`.
4. Заполните `access`, `prerequisites`, `maintenance` и `verification`. Не повышайте уровень проверки выше реально выполненного.
5. Добавьте проект в таблицу README и объясните изменение рекомендации в pull request.
6. Запустите локальные проверки:

```bash
python3 scripts/validate_catalog.py
python3 scripts/validate_guide.py
python3 -m py_compile scripts/*.py
```

При наличии GitHub-токена можно дополнительно сверить метаданные с API:

```bash
GH_TOKEN="$(gh auth token)" python3 scripts/audit_repositories.py
```

Онлайн-аудит проверяет доступность зафиксированного commit SHA, архивный статус, default branch и лицензию. Новые upstream commits и изменение `pushed_at` выводятся как обновления, но не делают обычный weekly-run красным: каталог остаётся воспроизводимо привязан к проверенному commit.

Перед обновлением каталога используйте строгий режим — он завершится ошибкой при любом upstream drift:

```bash
GH_TOKEN="$(gh auth token)" python3 scripts/audit_repositories.py --strict-upstream
```

Скрипт не запускает сторонний код. После строгого сигнала сначала прочитайте upstream diff, затем обновляйте `source_revision` и уровень доказательств.

## Уровни проверки

- `metadata` — проверены только метаданные репозитория.
- `docs` — изучены README и техническая документация.
- `artifact` — проверен релизный архив, update site или другой публикуемый артефакт.
- `cli-smoke` — выполнен безопасный smoke-test CLI без рабочей базы.
- `live-smoke` — проверен живой сервис или endpoint.
- `e2e` — пройден сценарий с требуемой платформой и тестовыми данными.

Непройденный этап описывайте в `verification.notes`, а выполненный подтверждайте ссылками в `verification.evidence_urls`.

## Стиль текста

- Пишите коротко и по делу.
- Сначала называйте задачу, затем технологию.
- Отделяйте подтверждённый факт от вывода автора.
- Не используйте «лучший», «production-ready» и «безопасный» без критериев и доказательств.
- Ссылки должны вести на первоисточники.

## Security

Не публикуйте уязвимости активных систем в обычном issue. Следуйте [SECURITY.md](SECURITY.md).
