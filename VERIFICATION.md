# Проверяемость AI × 1C Guide

Дата аудита: **2026-08-08**.

## Что означает статус

| Уровень | Что действительно сделано | Чего он не доказывает |
|---|---|---|
| `metadata` | Репозиторий и базовые GitHub-поля существуют | Корректность README и работоспособность |
| `docs` | README/документация и исходные claims сопоставлены с каталогом | Установку и runtime-поведение |
| `artifact` | Релиз скачан, checksum/архив/manifest проверены | Запуск внутри 1С или EDT |
| `cli-smoke` | Безопасная локальная команда реально выполнена | Работу со всеми ОС, tools и реальной базой |
| `live-smoke` | Реальный удалённый endpoint ответил на ограниченный набор вызовов | SLA, безопасность и полный API |
| `e2e` | Полный сценарий выполнен на заявленном стенде | Другие версии и окружения |

Ни у одного 1С-проекта в каталоге пока нет статуса `e2e` от этого гида.

## Подключения из проектов автора

Эти строки не повышают verification сторонних инструментов в каталоге. Они фиксируют границы конкретных интеграций автора, на основе которых написаны инструкции.

| Сценарий | Фактический результат | Граница проверки |
|---|---|---|
| OData 1С:Фреш → 1С:УНФ | По подтверждению автора, приватный endpoint прошёл Basic Auth и ограниченный GET `Catalog_Сотрудники`; в локальном `task2bitrix24` реализованы поиск дублей и POST непроведённых документов | Проверка не воспроизводилась независимо; при подготовке гайда write-flow не повторялся на одноразовой базе |
| Задачи Bitrix24 | `task2bitrix24` использует `tasks.task.list`, результаты, списания времени, пользователей, компании и проекты | Публичные примеры не вызывают приватный портал; `tasks.task.get` добавлен по официальной документации |
| Лид из `1cProductMap` | По подтверждению автора, через private server-side webhook выполнены `crm.lead.add` и `crm.lead.get`, записанные поля сверены | Публичный commit описывает архитектуру, но не содержит server source или transcript; новый `crm.item.add` не объявляется live-проверенным до отдельного теста |

Unit-тесты проверяют URL-кодирование кириллицы, JSON-обёртки `value` и legacy `d.results`, формы classic Bitrix24 REST, запрет redirects, привязку write-gates к endpoint, отсутствие сети у preview, отсутствие blind retry и маскирование чувствительных полей. Они не доказывают доступность внешних систем.

## Проверка каталога

Каждая запись schema v2 содержит:

- точный upstream commit (`source_revision`);
- дату последнего push и archive status;
- лицензию и источник сведений о ней;
- runtimes, платформы и prerequisites;
- доступ к исходникам, метаданным, бизнес-данным и внешним API;
- известные mutating/destructive operations;
- уровень проверки, evidence URLs и явное ограничение результата.

Локальные проверки:

```bash
python3 scripts/validate_catalog.py
python3 scripts/validate_guide.py
```

Сверка с GitHub API:

```bash
GH_TOKEN=... python3 scripts/audit_repositories.py
```

Токен нужен только для увеличения rate limit и не должен сохраняться в файлах или логах. Еженедельный workflow запускает сверку с временным `GITHUB_TOKEN`. Проверенный `source_revision` должен оставаться доступным; новый commit в upstream branch выводится как предупреждение и не меняет pin автоматически. Для ручного переаудита используйте `--strict-upstream`: тогда любой drift завершает команду ошибкой и требует сначала прочитать upstream diff.

## Что ещё нужно для end-to-end

Для каждого выбранного стека нужен отдельный test report:

1. ОС, версия платформы 1С/EDT, конфигурация и commit инструмента.
2. Одноразовая тестовая база и зафиксированный backup.
3. Точные команды установки и MCP config без секретов.
4. Позитивный smoke-test чтения с expected output.
5. Негативные тесты запрещённых операций.
6. Контрольные суммы или иной data-integrity check.
7. Проверка журналов, таймаутов и утечки секретов.
8. Rollback и фактическое восстановление.

Первый приоритет — три «золотых маршрута»: offline BSL review, read-only OData audit и Bitrix24 docs MCP + ограниченный runtime-коннектор.
